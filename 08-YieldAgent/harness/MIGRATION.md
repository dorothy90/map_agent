# 사내 백엔드로 이식하기

Python 3.11을 유지하며 Hermes를 별도로 설치하지 않는다. `harness/engine/`에 원본 엔진과 내부 의존 모듈을 포함했다. 기존 백엔드가 같은 Python 실행 파일로 내부 작업 프로세스를 시작하므로 서버를 하나 더 운영할 필요가 없다.

## 진행 원칙: 두 단계로 분리

| 단계 | 목표 | 완료 판단 |
|---|---|---|
| 1. 하네스 구조 이식 | 기존 사내 백엔드에서 내장 엔진과 실행·대화·저장 기능을 작동시킨다. | 검증용 도구를 사용한 실제 서버·LLM·저장소 통합 실행이 통과한다. |
| 2. 사내 에이전트 도구화 | 기존 에이전트의 실행 함수를 도구 어댑터로 연결한다. | 에이전트별 실제 업무 데이터와 질문으로 결과를 대조한다. |

**먼저 1단계만 수행한다. 1단계 완료 결과를 보고하고, 2단계를 진행하라는 사용자 지시를 받은 후 업무 에이전트를 연결한다.** 기존 사내 에이전트와 기존 서비스 경로는 보존한다. 1단계에서 업무 로직 재작성이나 수율 정답 개선까지 섞지 않는다.

## 시작 전: 기준 소스와 사내 구조 확인

기준 소스는 `codex/goal-driven-harness` 브랜치의 내장 엔진 구현 커밋 `b41fd1a` 시점 전체 파일과 이 문서의 후속 보완이다. 하네스가 없던 사내 버전에 해당 커밋 하나만 cherry-pick하면 이전 하네스 구현이 빠질 수 있다. 전체 소스 스냅샷을 별도 참조 폴더에 두고 필요한 구성을 병합한다.

1. 사내 저장소의 현재 변경을 확인하고 체크포인트 커밋 후 별도 이식 브랜치를 만든다. 기존 사용자 변경을 버리지 않는다.
2. 실제 서버 진입점, 초기화·종료 처리, 세션·인증, 스트리밍, DB 연결, 기존 에이전트 목록을 조사한다.
3. 원본 파일 → 사내 대응 파일 → 필요한 변경을 표로 기록한다. 사내 서버 파일 이름이 다르다는 이유로 원본 서버를 통째로 복사하지 않는다.
4. 기존 서비스의 대표 시나리오를 실행해 기준 결과를 남긴다. 설정·권한·의존성이 없어서 실행할 수 없으면 미검증 항목으로 명시한다.

## 1단계: 하네스 구조만 이식

### 구현 순서

1. **하네스 소스 복사:** `08-YieldAgent/harness/` 전체를 사내 프로젝트에 배치한다. `engine/`, 어댑터, 설정, 저장소, 스킬, 도구 인터페이스와 테스트를 포함하고 `__pycache__`·실제 데이터·테스트 산출물은 제외한다. 라이선스·원본 해시·패치 기록을 함께 보존한다.
2. **의존성 병합:** 루트 `requirements.txt`/`pyproject.toml`과 잠금 파일을 참고해 필요한 일반 패키지를 사내 의존성 목록에 병합한다. 사내 목록을 통째로 교체하지 않는다. Python 3.11 및 검증한 OpenAI SDK 2.24.0을 기준으로 충돌을 확인한다. `engine/pyproject.toml`은 원본 보존 자료이므로 설치 대상으로 사용하지 않는다.
3. **서버 연결:** 원본 `agent_server.py`의 하네스 초기화·종료, 세션 선택, 실행·취소·후속 요청, SSE, 결과·산출물 조회 연결부를 사내 서버에 병합한다. 기존 서비스 경로와 인증을 보존하고 principal을 사내 사용자 식별자에 연결한다. 전체 서버 파일을 덮어쓰지 않는다.
4. **검증용 도구 연결:** 외부 업무 시스템에 의존하지 않는 읽기 전용 도구로 입력과 결과 저장을 확인한다. 기존 수율 도구를 모두 등록하면 Oracle·맵 모듈까지 의존하므로, 1단계 테스트에서는 최소 레지스트리를 사용한다. 현재 `RunController(..., registry_factory=...)`가 주입 지점이다. `harness/app.py`의 컨트롤러 생성 위치 또는 사내의 대응 위치에서 검증용 팩터리를 전달한다. `domain_registry()`나 기존 업무 도구 구현을 삭제해 우회하지 않는다. 운영에서는 검증용 도구가 노출되지 않도록 분리한다.
5. **프롬프트·스킬 확인:** `instructions/native.md`, `skills/` 및 사용자 프로필의 자동 로딩 설정을 조사한다. 원본 수율 전용 스킬이 미연결 업무 도구를 호출하도록 유도하지 않게 1단계 검증 설정을 분리한다. 스킬 탐색·읽기 자체는 실제 엔진으로 검증하며, 원본 업무 스킬은 2단계 연결용으로 보존한다. 기존 프로필은 스킬이 이미 존재하면 자동 덮어쓰지 않으므로, 소스 변경만으로 프로필까지 갱신됐다고 가정하지 않는다.
6. **환경 연결:** `.env.example`의 `HARNESS_*`를 참고해 테스트용 MongoDB, 실제 사내 LLM, 사용자별 프로필 저장 위치를 설정한다. 검증 경로에서 `HARNESS_ENABLED=true`, `HARNESS_ENGINE=hermes`로 실행한다. 기존 세션은 저장된 엔진을 유지하므로 새 세션을 사용한다. 비밀값은 코드·문서·로그에 기록하지 않는다.

### 1단계 완료 기준

- 별도 Hermes 설치·외부 소스 경로·Python 3.14 없이 Python 3.11에서 시작된다.
- 실제 사내 서버에 요청했을 때 실제 LLM이 검증용 도구를 선택·실행하고, 결과가 MongoDB에 저장되며 사용자 응답까지 전달된다. 도구 함수를 직접 호출한 것만으로 통합 성공으로 판단하지 않는다.
- 같은 세션의 후속 질문에서 앞선 대화·결과를 참조한다. 다른 사용자·세션에서는 해당 결과에 접근할 수 없다.
- 스킬 읽기, 진행 이벤트, 실행 취소, 실패·시간 제한 처리가 확인된다. 프로세스 재시작 시 저장된 실행 상태가 어떻게 처리되는지 확인하고, 이어 실행이 지원되지 않는 경우도 명확히 기록한다.
- 기존 사내 서비스의 기준 시나리오가 유지된다.
- 변경 파일, 설정·패키지 변경, 실제 실행 기록, 통과·실패·미검증 항목, 원래 경로로 되돌리는 방법을 보고한다. 이 시점에 **하네스 구조 이식 완료**만 선언하고 업무 정답 검증 완료로 표현하지 않는다.

검증용 도구의 데이터는 합성 데이터임을 명시한다. 1단계는 실제 LLM·서버·MongoDB를 사용한 기반 구조 검증이고, Oracle 등 업무 DB와 업무 에이전트 검증은 2단계에서 수행한다.

## 2단계: 기존 사내 에이전트를 도구로 연결

사용자의 2단계 진행 지시 후 에이전트 하나씩 연결한다. 기존 에이전트 내부를 전부 재작성하지 않는다.

1. 에이전트의 실행 함수, 입력·출력, 의존 서비스, 읽기·쓰기 효과, 오류·취소 동작을 조사한다. 내부에서 별도 LLM을 호출한다면 모델 설정과 호출 비용·시간도 기록한다.
2. `harness/tools/`에 어댑터를 추가한다. 입력 스키마와 도구 설명을 정의하고, 기존 실행 함수를 호출한 결과를 `ToolResult`로 변환한다. 범위·단위·전체성·오류·산출물을 보존한다. 함수가 동기식으로 오래 실행된다면 기존 격리 실행 방식을 검토한다.
3. `harness/tools/registry.py`의 `domain_registry()` 또는 사내에서 구성한 레지스트리 팩터리에 `ToolSpec`을 등록한다. **현재 내장 엔진은 `read`와 `artifact` 효과 도구만 노출한다.** 영구 쓰기 에이전트를 읽기 도구로 잘못 표시해서 연결하지 않는다. 쓰기 기능은 별도 권한·승인 계약이 필요하므로 이 단계의 읽기 도구 연결과 구분한다.
4. 연결한 도구의 실제 기능에 맞춰 설명·스킬을 보완한다. 특정 질문의 키워드·정규식 분기나 반복적인 예시 추가로 모델의 계획 실패를 우회하지 않는다.
5. 실제 업무 DB·LLM·도구를 연결해 기존 에이전트 직접 실행 결과와 하네스 경유 결과를 대조한다. 정상·빈 결과·오류·후속 질문·취소를 검사하고, 해당 에이전트가 통과한 후 다음 것을 연결한다.

예: 기존 `수율 에이전트 실행 함수`를 `query_yield` 같은 도구로 감싼다. 하네스가 질문에 맞춰 도구를 선택하고, 어댑터가 기존 함수를 실행하며, 조회 결과와 범위를 저장해 모델에 반환한다. 이 예시는 함수명이나 사내 구현이 동일하다고 가정하라는 뜻이 아니다.

### 2단계 완료 기준

연결 대상 에이전트별 실제 업무 시나리오가 통과하고, 여러 도구를 조합하는 질문과 후속 질문에서도 올바른 범위·출처·산출물이 유지되어야 한다. 하네스가 답변 텍스트를 반환했다는 사실만으로 업무 정답으로 판정하지 않는다.

## 6-luna에게 전달할 작업 지시

아래 지시와 이 문서를 함께 제공한다.

> 이 문서에 따라 **1단계 하네스 구조 이식만 먼저 수행해라.** 기준 소스와 사내 코드를 먼저 조사하고 파일 대응표를 만든 뒤, 기존 기능을 보존하며 순서대로 구현해라. Python 3.11을 유지하고 Hermes를 별도로 설치하지 마라. 업무 에이전트를 삭제하거나 내부 로직을 재작성하지 말고, 1단계에서는 검증용 최소 도구 레지스트리로 실행해라. 실제 서버·LLM·MongoDB를 연결해 도구 실행·이력·스킬·취소를 검증하고 기존 기능 회귀 여부를 확인해라. 실행하지 못한 검증은 성공으로 보고하지 마라. 완료 후 변경 내역과 검증 증거·남은 문제를 보고하고, 업무 에이전트 도구화는 2단계 진행 지시를 받은 뒤 시작해라.

## 런타임 데이터

`.runtime/hermes/src`, `.venv-hermes`, 원본 Hermes Git 저장소는 필요 없다. `.runtime/hermes/profiles/`는 설치 파일이 아니라 사용자별 스킬·메모리 실행 데이터이며 쓰기 가능한 저장 공간이 필요하다. 기존 메모리를 보존하려면 이 데이터는 별도 이관한다.

## 포함된 본체 위치

| 역할 | 내부 소스 |
|---|---|
| 진입점·대화 실행 | `engine/run_agent.py`, `engine/agent/` |
| 도구 검색·설명·호출 | `engine/model_tools.py`, `engine/tools/registry.py`, `engine/tools/tool_search.py` |
| 스킬·메모리 | `engine/tools/skills_tool.py`, `engine/tools/memory_tool.py` 및 관련 모듈 |
| 백엔드 도구 연결 | `native_worker.py`, `native_hermes.py`, `tools/registry.py`, `executor.py` |
| 원본 추적 | `engine/UPSTREAM.json`, `engine/PATCHES.diff`, `engine/LICENSE` |

엔진의 내부 import 의존성 때문에 CLI·플러그인 관련 소스도 일부 포함되어 있지만 해당 제품 기능을 백엔드에 노출하지는 않는다. 런타임에 패키지를 설치하거나 엔진을 업데이트하지 않는다. 필요한 선택 패키지가 없으면 사내 패키지 절차로 준비해야 한다.

## 검증 명령과 현재 한계

승인된 패키지를 준비한 후 `BACKEND_PYTHON=/path/to/python bash scripts/setup_hermes.sh`로 import를 확인한다. `harness/tests/test_native_transport.py`는 다른 경로로 복사한 실제 엔진을 로컬 가상 모델과 연결해 스킬·도구 호출·취소를 검사한다.

이 검사는 실제 업무 정답을 보장하지 않는다. 아래 업무 검증은 2단계에 해당한다. 사내 DB와 실제 LLM을 연결한 사용자 시나리오에서 조회 기간, 열화 파라미터 전체 집합, 수율 정의, 모집단 및 하위 10개 선정, 맵 10개를 각각 확인한 후 운영 전환한다. 기존 실제 평가에서 기간·지표 해석 오류와 토큰 예산 중단이 있었으므로, 이식 성공과 답변 품질 통과를 구분한다.
