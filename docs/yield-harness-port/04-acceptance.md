# 사내 레포에 반영한 파일 검수

01에서 만든 `REF`는 고정 원본, `DEST`는 사내 브랜치, `AUDIT/plan.tsv`는 사내에서 정한 목적지와 처리 방식이다. 다음 순서로 파일 이식을 마무리한다.

1. **참조본 무결성.** `python3 "$KIT/build_kit.py" verify-tree --root "$REF" --inventory "$KIT/FILES.tsv"`가 성공하는지 확인한다. 아래 사내 작업은 이 참조본을 기준으로 한다.
2. **ADD와 KEEP.** 각 행의 원본 경로와 사내 목적지를 대조한다. 새 파일과 그대로 쓰기로 한 파일은 FILES.tsv의 SHA-256과 Git 실행 비트가 일치해야 한다. 아래 검사는 재배치한 파일도 destination 열로 찾는다. 키 이름을 유지한 UTF-8 TSV를 사용한다.
3. **MERGE.** 양쪽 내용이 달라야 하는 파일은 양쪽 경로, 사내에서 보존한 기능, 가져온 함수나 계약, 검토 근거를 기록한다. 각 행을 실제 diff에서 확인한다. 특히 공용 DB 연결, 사용자 인증, 엔진 로딩, 도구 등록, 웹 진입점을 확인한다. 수동 병합한 파일은 참조본과 해시가 다를 수 있다.
4. **HOLD.** 보류 이유·대체 파일·담당자를 사내 기록에 남긴다. 필수 파일이 보류 중이면 해당 기능을 미완료로 표시한다. 기존 앱 체크포인트에서 삭제된 여섯 경로는 CHECKPOINT-144.tsv에 이력으로 남아 있다. 사내 다른 코드가 참조하는 경로를 자동 삭제하지 않는다.
5. **변경 범위.** 아래 Git 명령으로 추적 중인 변경, 새 파일, 스테이징된 변경을 함께 본다. 정상적으로 추가할 파일이 표시되지 않으면 `git check-ignore -v -- 상대경로`로 사내 무시 규칙을 확인한다. 필요한 경로만 선별해 스테이징한 뒤 검토한다. 특히 기존 프론트의 잠금 파일과 실행 스크립트의 모드를 확인한다.

```bash
python3 - "$KIT" "$DEST" "$AUDIT/plan.tsv" <<'PY'
import sys
from pathlib import Path
kit, dest, sheet = map(Path, sys.argv[1:])
sys.path.insert(0, str(kit))
from port_plan import table, location, identical
rows = {r['path']: r for r in table(kit / 'FILES.tsv')}
decisions = table(sheet)
assert len(rows) == len(decisions) and set(rows) == {d['path'] for d in decisions}
checked = 0
for d in decisions:
    if d['action'] in ('ADD', 'KEEP'):
        if not identical(location(dest, d['destination']), rows[d['path']]):
            sys.exit('확인 필요 ' + d['destination'])
        checked += 1
print(f'원본과 일치하는 ADD/KEEP 파일 {checked}개. MERGE/HOLD는 대응표에서 별도로 검토하세요.')
PY
git -C "$DEST" status --short --untracked-files=all
git -C "$DEST" diff --stat
git -C "$DEST" diff --cached --stat
git -C "$DEST" diff --cached --check
```

**완료 기록**에는 외부 기준 커밋, 사내 시작·종료 커밋, ADD/KEEP/MERGE/HOLD 수량, 실제 검수 결과, 미결 항목을 남긴다. FILES.tsv의 4,847개 경로 모두에 결정이 있고 필수 기능에 미결이 없는지 확인한다. 빈 사내 레포와 이미 코드가 있는 사내 레포는 ADD 수가 다르다.

**이미 사내 환경에서 기존 프로그램을 실행할 수 있다면** 새 채팅에서 수율일보를 요청하고 사내 DB 제품 하나를 선택한다. 월 3·주 4·일 3개 기간, 열화·개선 각 3개 웨이퍼 산점도, 검사별 직전 주·최근 주·델타 BIN 맵을 동일한 DB 조건으로 대조한다. 스킬을 옮겼다면 새 채팅의 스킬 목록도 확인한다. 실행 환경이 준비되지 않은 경우 파일 검수와 기능 검증의 완료 여부를 각각 기록한다.

## Ubuntu 배포 전 직원별 파일 격리

**배포 전 필수 · 미검증 (2026-11-24).** [macOS 전체 테스트 결과](VERIFICATION.md#stock-only)에서 건너뛴 유일한 검사다. 아래 명령을 Ubuntu에서 실행한 뒤 대상 커밋, 실행 일시, 종료 코드와 결과를 사내 검수표에 기록한다.

이식할 때 현재 브랜치의 [배포 검증 명령](../../08-YieldAgent/harness/evals/ubuntu_isolation.py)과 [직원별 격리 테스트](../../08-YieldAgent/harness/tests/test_linux_local_transport.py)를 함께 반영한다.

Ubuntu 배포 호스트에서 웹 백엔드를 실행할 일반 서비스 계정과 같은 환경 설정으로 다음 명령을 실행한다. 저장소 루트에서 서버 가상환경의 Python을 사용한다. 이 가상환경에는 pytest가 필요하다. 별도의 분석 가상환경을 쓰는 배포에서는 서비스 설정의 `HARNESS_ISOLATION_ANALYSIS_VENV`를 그대로 사용한다.

```sh
PYTHONPATH=08-YieldAgent .venv/bin/python -m harness.evals.ubuntu_isolation
```

검사는 임시 작업 폴더에 직원 A의 CSV를 만들고 실제 `bwrap` 안에서 합계 42를 읽는다. 같은 실행 번호를 쓴 직원 B의 Python에서는 그 파일을 읽을 수 없어야 한다. 명령이 종료 코드 0과 `1 passed`를 반환해야 배포를 진행한다. 실행 실패나 건너뜀은 배포 전 확인이 미완료된 상태다.

## 채팅별 Python 상태와 엑셀 다운로드

1. 새 웹 채팅에서 Python으로 임의 바이트를 생성해 변수에 보관하고 SHA-256만 출력하게 한다. 다음 메시지에서 같은 변수의 원래 바이트를 출력하게 한다. 두 번째 호출에서 변수를 다시 대입하지 않았는지 확인하고, 반환된 바이트의 SHA-256을 첫 답변과 대조한다.
2. 같은 채팅에서 사내 DB에 있는 LOT·웨이퍼 하나의 PT1H 맵을 조회한 뒤, 그 맵 이미지를 넣은 엑셀 파일을 요청한다. 답변의 첨부 버튼을 눌러 받은 파일을 Excel에서 열고, 시트에 맵 그림이 들어 있으며 LOT·웨이퍼·좌표 및 BIN별 수량이 DB와 일치하는지 확인한다.
3. 같은 직원의 다른 채팅과 다른 직원 세션에서는 이전 Python 변수가 보이지 않아야 한다. 다른 채팅·직원으로 첫 채팅의 파일을 요청했을 때 다운로드가 거부되는지도 확인한다. Ubuntu에서는 위의 배포 전 직원별 파일 격리 검사도 실행한다.

## RCP별 누적 맵으로 대화 이력 확인

1. 검증 환경에서 사용하도록 승인된 모델의 실제 요청 ID를 기록한다. 개발 기준 모델은 OpenRouter의 `z-ai/glm-5.3-flash`다. 모델이 다르면 결과에 사용 모델을 명시한다.
2. 새 채팅에서 데이터가 있는 제조 공정의 RCP별 누적 맵을 요청하고 제품·맵 검사·기간을 먼저 고른다. 이어서 “같은 조건으로 RCP별 누적 맵을 다시 보여줘.”라고 보낸다.
3. 후속 질문의 모델 입력에 기존 선택 응답이 들어 있는지 확인한다. 모델이 작성한 `load_wafer_maps` 인자와 실제 호출 인자의 제품(`lot_cd`), 검사(`oper`), 기간, 그룹 기준(`aggregate.group_by`), 제조 공정(`aggregate.group_oper`)을 대조한다.
4. 두 답변에서 RCP별 맵과 표를 열고 동일한 기간·검사·공정으로 독립 조회한 DB 수량과 비교한다. 공정 이력 미매칭 건수도 기록한다. [개발 더미 DB에서 검증한 결과와 화면](VERIFICATION.md#glm-map)

### 직원별 자동 검색과 공정명 검수

- 새 채팅의 첫 모델 요청에서 자동 검색 도구와 검색 가능한 수율 도구 목록을 확인한다. 개발 GLM 설정에서는 직접 제공되는 도구가 12개다. 이미지 도구는 공급자의 지원 여부에 따라 달라진다. 수율 도구 6개, 대화 검색, 할 일 목록은 자동 검색으로 불러온다. 이전 버전의 채팅도 다시 열어 현재 직원의 허용 범위를 대조한다. 다른 직원의 세션·결과 접근이 거부되는지도 확인한다.
- 정확한 공정명과 오타를 각각 별도 새 채팅에서 시험한다. 첫 맵 호출의 공정명, 반환된 오류, 공정 목록 조회, 재호출 인자를 순서대로 기록한다. 모델이 오타를 먼저 고치면 그렇게 기록한다. 실제 DB 목록을 확인한 경우와 구분해야 한다.
- 호출 수를 셀 때 모델의 `tool_call`과 그 안에서 실행된 `load_wafer_maps`를 별도 열에 기록한다. 스킬 저장 여부와 재시도 횟수는 실행마다 달라질 수 있다. [개발 기준 관찰값](VERIFICATION.md#native-discovery)

### 공용 입력과 세션별 결과 검수

1. 공용 입력 폴더의 CSV에 검증할 LOT·웨이퍼·검사를 한 건 지정한다. 같은 계정으로 새 채팅 두 개를 열고 각각 같은 CSV를 읽어 DB 수율 표와 BIN 맵을 표시하도록 요청한다. 두 화면의 수율과 맵 좌표·통과 판정을 사내 DB와 대조한다.
2. 두 채팅에서 표 데이터와 맵의 결과 주소를 기록한다. 원래 세션으로 열면 200이고, 같은 계정에서 상대 세션 ID로 바꾸면 양방향 모두 404여야 한다. 폴더 밖에 둔 검증용 파일과 그 파일을 가리키는 심볼릭 링크의 읽기도 거부되는지 확인한다.
3. 해당 공급자가 이미지를 지원하면 공용 폴더의 테스트 PNG를 열어 실제 도형과 답변을 비교한다. 같은 채팅에 후속 질문을 보내 Hermes가 저장한 직전 답변과 도구 결과가 모델 입력에 복원되는지도 확인한다.

### 구형 실행 제거 후 검수

1. 새 웹 대화에서 DB 수율을 조회하고 같은 대화에서 스킬과 후속 질문을 실행한다. 각 실행 기록의 `native_engine.entrypoint`가 `stock_chat`인지 확인한다.
2. 수율 도구를 끈 모델 평가와 가상 자료를 사용하는 모델 평가에서도 같은 값을 확인한다. 가상 자료 평가에서는 세션에 저장한 입력을 읽어 계산하고, 다음 질문에서 그 결과를 재사용한다.
3. 이전에 완료하거나 취소한 대화의 메시지와 상태를 읽을 수 있는지 확인한다. 테스트와 실행 경로의 일치를 확인할 때는 검수할 커밋을 새로 받은 작업 폴더에서 전체 하네스 테스트를 실행한다.
