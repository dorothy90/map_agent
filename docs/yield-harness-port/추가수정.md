# 기본 이식 후 2a45e76f 추가 수정 적용

## 1. 범위와 기준 커밋

담당자는 기본 안내서의 이식을 마친 사내 저장소에 이 절차를 적용한다. 이 문서는 기존 안내서와 `FILES.tsv`를 대체하지 않는다. 기본 안내서와 `FILES.tsv`의 기준은 `e45242bc`로 유지한다. 이번 추가 수정 때문에 `FILES.tsv`를 재생성하지 않는다.

| 구분 | 커밋 | 내용 |
|---|---|---|
| 기본 안내서 HEAD | `e45242bc7d9a7199be9ed6378e53c109585d89db` | 이미 적용한 기본 이식 기준 |
| 추가 수정 대상 | `2a45e76f9a4a24616b6a3e9be90be2a0702e9f45` | `fix(harness): 로컬 게이트웨이 접속 제한 제거와 ProcessRuntime 채팅 ID 전달` |
| 중간 커밋 | `cfc51f318ec11e4aaeefaa1320844cf74b6e1348` | `Add internal harness transplant and validation guidelines`. `261125_이식_prompt`만 추가 |
| 브랜치 끝 병합 커밋 | `fe823a761963aaaba2d86cb89fd17d54b663d3cd` | 이번 적용 대상 아님 |

`git diff e45242bc..2a45e76f`의 11개 경로만 적용한다. `261125_이식_prompt`와 병합 커밋은 적용하지 않는다. 대상 11개 경로에 대한 `git diff 2a45e76f fe823a76 -- <경로들>`은 비어 있다. 병합 커밋은 이 파일들을 바꾸지 않는다.

원본 참조 저장소에서 범위와 파일별 hunk를 확인한다. 아래 `PATH`는 2절의 실제 경로로 바꾼다.

```bash
git diff --name-status e45242bc..2a45e76f
git show 2a45e76f -- PATH
git diff e45242bc..2a45e76f -- PATH
git show 2a45e76f:PATH | shasum -a 256
git ls-tree 2a45e76f -- PATH
```

PowerShell에서는 같은 blob을 다음 명령으로 확인한다.

```powershell
git show 2a45e76f:PATH | python -c "import hashlib,sys; print(hashlib.sha256(sys.stdin.buffer.read()).hexdigest())"
git ls-tree 2a45e76f -- PATH
```

원본 커밋을 확인할 수 없으면 적용을 진행하지 않는다. 결과표에 확인하지 못한 단계와 사유를 남긴다.

사내 수정이 없는 파일은 원본 blob의 해시와 크기를 대조한다. Windows 작업 파일은 줄바꿈 변환 때문에 해시가 달라질 수 있으므로 원본 blob과 구분한다. 사내 수정이 있는 파일은 전체 파일을 덮어쓰지 않는다. 해당 hunk와 사내 코드를 비교한다. 병합한 파일의 해시는 위 원본 값과 다를 수 있으므로 적용한 hunk와 보존한 사내 변경을 기록한다.

### 2.1. `08-YieldAgent/harness/dev/local_gateway_app.py`

Host 허용 목록과 `local_peer` 검사를 제거한다. `Local host only`와 `Origin rejected`로 반환하던 403을 제거한다. 이에만 쓰던 상수와 import도 diff대로 제거한다. Swagger와 LAN 접속이 로컬 Host·Origin 검사에서 거부되지 않도록 한다.

`FixedLocalPrincipal.resolve`는 접속 주소와 관계없이 `HARNESS_PRINCIPAL`로 설정한 사용자의 `Principal`을 반환한다. `file_ticket_required = True`는 유지한다. `FixedLocalPrincipal.allows`는 모든 WebSocket Origin에 `True`를 반환한다.

`CORSMiddleware`에 `allow_origins=['*']`, `allow_methods=['*']`, `allow_headers=['*']`를 지정한다. credentials 허용은 추가하지 않는다. HTTP 미들웨어 이름은 `local_principal`로 바꾼다. `principal_id` 설정과 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`은 유지한다. 이 변경은 로컬 개발 게이트웨이에만 적용한다.

### 2.2. `08-YieldAgent/harness/app.py`

`/health/isolation`에서 요청 주소가 `127.0.0.1`, `::1`, `localhost`가 아니면 `local health check only` 403을 반환하던 조건을 제거한다. 기존 `ProcessRuntime` 호출에 `session_id="health"`를 전달한다. Windows 분기의 기존 준비·정리 흐름은 바꾸지 않는다.

### 2.3. `08-YieldAgent/harness/dev/launch_local_gateway.sh`

기본 바인드 주소를 `127.0.0.1`에서 `0.0.0.0`으로 바꾼다. `HOST="${HARNESS_GATEWAY_HOST:-0.0.0.0}"`로 환경 변수 재정의를 유지한다. 주석을 LAN 접속과 전체 인터페이스 기본 바인드에 맞춘다. 포트 기본값 `61302`와 실행 명령은 유지한다. 실행 모드는 `100755`로 유지한다.

### 2.4. `08-YieldAgent/harness_console/vite.config.ts`

`server.host`를 `process.env.HARNESS_WEB_HOST || '0.0.0.0'`으로 바꾼다. 개발 화면의 LAN 접속과 환경 변수 재정의를 허용한다. 프록시 대상과 포트는 바꾸지 않는다.

### 2.5. `docs/yield-harness-port/06-windows-chat.md`

사내에 적용한 안내서에서 uvicorn과 npm 명령의 `--host 127.0.0.1` 두 곳만 `--host 0.0.0.0`으로 바꾼다. 서버 바인드 안내를 변경된 기본 동작에 맞춘다. `Invoke-RestMethod`, 브라우저 주소, `HARNESS_GATEWAY_TARGET`의 클라이언트 URL은 `127.0.0.1`로 유지한다. 기본 안내서 묶음과 `FILES.tsv`의 기준 커밋은 바꾸지 않는다.

### 2.6. `08-YieldAgent/harness/README.md`

로컬 게이트웨이 실행 안내에 `HARNESS_GATEWAY_HOST`의 기본값이 `0.0.0.0`이라는 한 문장을 추가한다. 실행 안내와 스크립트의 기본값을 맞춘다.

### 2.7. `08-YieldAgent/harness/runtime/process.py`

`ProcessRuntime.__init__`에 기본값이 `None`인 `session_id`를 추가한다. `isolation_backend(isolation, run_id, principal_id, session_id)`로 전달한다. 호출자가 지정한 채팅 ID가 격리 백엔드까지 도달하도록 한다.

### 2.8. `08-YieldAgent/harness/evals/preflight.py`

`ProcessRuntime` 호출에 `session_id="preflight"`를 추가한다. 채팅 ID가 필요한 격리 백엔드에서도 사전 검사를 실행하도록 한다.

### 2.9. `08-YieldAgent/harness/tests/test_local_gateway_app.py`

새 파일로 추가한다. `e45242bc`에는 없으므로 기존 원본과 병합하는 파일이 아니다. 사내에 같은 경로의 파일이 이미 있으면 출처와 내용을 먼저 비교한다.

Swagger 페이지 Origin, Host `localhost`, Origin 없음, LAN 형태 Host로 보내는 `POST /runs`를 검사한다. 테스트용 라우트의 기대 응답은 200이며 고정 principal과 응답 헤더도 확인한다. CORS preflight와 credentials 미허용을 검사한다. `FixedLocalPrincipal`이 비로컬 접속과 여러 WebSocket Origin을 허용하는지 검사한다. 이 테스트의 200 응답을 실제 `/runs` 실행 성공으로 기록하지 않는다.

### 2.10. `08-YieldAgent/harness/tests/test_isolation_runtime.py`

`test_process_runtime_passes_session_id_to_backend`를 추가한다. `isolation_backend`를 monkeypatch로 바꿔 호출 인자를 수집한다. `session_id` 전달과 반환 백엔드의 보관을 확인한다.

### 2.11. `08-YieldAgent/harness/tests/test_preflight.py`

`assert calls[0]['session_id'] == 'preflight'`를 추가한다. 사전 검사에서 고정 검사용 채팅 ID를 전달하는지 확인한다.

## 3. 사내 적용 규칙

`engine/**`는 수정하지 않는다. `08-YieldAgent/harness/engine/**`도 이번 적용 범위에 포함하지 않는다. 2절의 11개 경로에서 대상 커밋의 hunk만 적용한다. 사내 인증, DB 연결, SSO, 사내 게이트웨이의 기존 코드는 보존한다.

로컬 개발 게이트웨이는 loopback·Origin 제한을 제거하고 기본적으로 `0.0.0.0`에 바인드한다. 별도 로그인은 추가하지 않는다. 모든 요청은 고정 `HARNESS_PRINCIPAL`로 실행된다. 이 변경을 사내 운영 게이트웨이나 SSO 게이트웨이에 적용하지 않는다.

대상 파일을 적용하려면 사내 코드를 삭제해야 하는 경우 해당 파일을 `차단`으로 기록한다. 해당 파일의 적용을 중단한다. 원본 경로, 사내 경로, 충돌 hunk, 보존해야 할 동작을 기록한다. `engine/**` 수정이 필요한 경우에도 해당 파일이나 검사를 `차단`으로 기록한다. 차단 파일에 의존하는 검사는 진행하지 않는다. 독립적인 나머지 파일은 계속 적용한다.

## 4. 적용 순서

사내 저장소의 기준 커밋과 현재 변경 목록을 먼저 기록한다. 원본 참조 저장소에서 1절 명령으로 11개 경로를 확인한다. 사내 경로가 다르면 원본 경로와 사내 목적지를 대응시킨다.

1. `harness/runtime/process.py`에 `session_id` 인자와 전달을 적용한다.
2. `harness/evals/preflight.py`와 `harness/tests/test_isolation_runtime.py`, `harness/tests/test_preflight.py`에 대응 hunk를 적용한다.
3. `harness/app.py`에 상태 확인 제한 제거와 `session_id="health"`를 적용한다.
4. `harness/dev/local_gateway_app.py`에 로컬 게이트웨이 변경을 적용한다.
5. `harness/dev/launch_local_gateway.sh`와 `harness_console/vite.config.ts`에 바인드 주소 변경을 적용한다.
6. `harness/README.md`와 사내의 `docs/yield-harness-port/06-windows-chat.md`에 안내 문구 hunk를 적용한다.
7. `harness/tests/test_local_gateway_app.py`를 새 파일로 추가한다.
8. 원본과 사내 diff를 대조한다.
9. 5절의 검증을 실행한다.

위 목록의 `harness/`와 `harness_console/`는 `08-YieldAgent/` 아래 경로이다. shell 실행 비트가 사라졌으면 POSIX 환경에서 다음 명령으로 복구한다.

```bash
chmod 755 08-YieldAgent/harness/dev/launch_local_gateway.sh
test -x 08-YieldAgent/harness/dev/launch_local_gateway.sh
git diff --summary -- 08-YieldAgent/harness/dev/launch_local_gateway.sh
git ls-files --stage -- 08-YieldAgent/harness/dev/launch_local_gateway.sh
```

모드 변경 diff가 없어야 한다. Git에 기록된 mode는 `100755`여야 한다. Windows에서 실행 비트를 검증할 수 없으면 해당 검사를 `미검증`으로 기록한다. 내용을 복사한 뒤 Git mode가 `100644`이면 `git update-index --chmod=+x -- 08-YieldAgent/harness/dev/launch_local_gateway.sh`를 실행하고 `git ls-files --stage`로 `100755`를 확인한다.

### 5.2. 로컬 게이트웨이 기동과 POST 확인

Windows에서는 `06-windows-chat.md`의 환경 준비와 실행기 검사를 먼저 수행한다. 2.5절의 두 바인드 hunk를 반영한 명령으로 로컬 게이트웨이를 기동한다. Bash 환경에서는 준비된 가상환경을 활성화한 뒤 `08-YieldAgent/harness/dev/launch_local_gateway.sh`를 실행한다. 이 스크립트의 기본 포트는 `61302`이다.

게이트웨이가 기동하면 별도 터미널에서 세 요청을 보낸다. 아래 예시는 Windows 안내서의 게이트웨이 포트 `61402`를 사용한다. 다른 포트로 기동했으면 URL, Origin, Host 헤더의 포트를 함께 바꾼다. Origin에는 게이트웨이 페이지 자체의 주소를 사용한다.

Bash에서는 다음 명령을 실행한다.

```bash
gateway_url='http://127.0.0.1:61402'
curl -sS -o /dev/null -w 'Swagger Origin: %{http_code}\n' \
  -H "Origin: $gateway_url" -H 'Content-Type: application/json' \
  --data '{}' "$gateway_url/runs"
curl -sS -o /dev/null -w 'Host localhost: %{http_code}\n' \
  -H 'Host: localhost:61402' -H "Origin: $gateway_url" \
  -H 'Content-Type: application/json' --data '{}' "$gateway_url/runs"
curl -sS -o /dev/null -w 'No Origin: %{http_code}\n' \
  -H 'Content-Type: application/json' --data '{}' "$gateway_url/runs"
```

PowerShell에서는 별칭과 구분하여 `curl.exe`를 실행한다.

```powershell
$gatewayUrl = 'http://127.0.0.1:61402'
curl.exe -sS -o NUL -w 'Swagger Origin: %{http_code}\n' `
  -H "Origin: $gatewayUrl" -H 'Content-Type: application/json' `
  --data '{}' "$gatewayUrl/runs"
curl.exe -sS -o NUL -w 'Host localhost: %{http_code}\n' `
  -H 'Host: localhost:61402' -H "Origin: $gatewayUrl" `
  -H 'Content-Type: application/json' --data '{}' "$gatewayUrl/runs"
curl.exe -sS -o NUL -w 'No Origin: %{http_code}\n' `
  -H 'Content-Type: application/json' --data '{}' "$gatewayUrl/runs"
```

세 요청 모두 403이 아니어야 한다. 빈 JSON이나 필수 필드가 없는 JSON의 422는 이 접속 제한 검사에서 허용한다. 422는 분석 실행 성공을 뜻하지 않는다. 연결 실패나 5xx는 통과로 처리하지 않는다. 실제 HTTP 상태와 실행 환경을 각각 기록한다.

### 5.3. Windows 사전 검사와 격리 상태 확인

`config.get`, `config.set`, `session.steer`를 실행 RPC로 연결한다. config 요청은 `key=='busy'`만 허용하고 다른 키는 unsupported로 처리한다. `message.start`의 `carryover_id`와 새 활성 run의 `run_id`가 같으면 live run 바인딩을 갱신하여 후속 steer가 새 run을 향하도록 한다.

#### 2.4. `08-YieldAgent/harness/gateway/execution.py`

`Execution.busy_config`가 `config.get/config.set`으로 principal별 Mongo `gateway_settings.busy`를 읽고 저장하며, 저장값이 없으면 `steer`를 반환한다. 구현된 키는 `busy`뿐이고 값은 `steer`, `queue`, `interrupt`이다. `Execution.steer`는 활성 run의 `steer_inbox`에 `{id,text,at}`와 `steer.accepted` 이벤트를 함께 추가하고 `{status:'queued'}`를 반환한다. 빈 문자열·너무 긴 문자열, 비활성 run(`execution_not_ready`), 오래된 generation을 거부한다. `submit_values`에서 `prompt.submit`의 `queued` 플래그를 허용하며 일반적인 배타적 실행 접수는 유지한다.

### 3. 사내 적용 규칙

담당자는 이 배치 2절의 39개 경로에서 `cb8feec2` hunk만 적용한다. 사내 인증·SSO·DB 연결과 기존 사내 코드를 보존한다. 이 배치는 바인드 주소 변경이 아니므로 앞선 절의 로컬 개발 전용 Host·Origin·바인드 변경을 여기서 다시 적용하지 않는다.

`engine/**`와 `08-YieldAgent/harness/engine/**`는 수정하지 않는다. 테스트를 맞추기 위해 engine을 변경하지 않는다. 두 manifest는 커밋된 blob을 사용하며 임의로 재작성하지 않는다. 해당 blob이나 hunk를 적용하려면 사내 코드를 삭제해야 하는 경우 그 파일을 `차단`으로 기록한다. 사내 경로, 충돌 hunk, 보존해야 할 동작을 적고 해당 파일 및 이에 의존하는 검사를 중단한다. 독립적인 나머지 파일은 계속 적용한다.

### 4. 적용 순서

사내 기준 커밋과 현재 변경 목록을 먼저 기록한다. 이 추가 문서의 1절 명령으로 원본 39개 경로를 확인하고 사내 목적지와 대응시킨다. 아래 경로는 `08-YieldAgent/` 아래이다.

1. `harness_console/src/hermes/store/busy-input-mode.ts`, `src/hermes/lib/chat-messages/types.ts`, `src/hermes/i18n/types.ts`에 기본 모드와 타입 변경을 적용한다. 두 번째·세 번째 경로도 `harness_console/` 아래이다.
2. `harness/gateway/rpc_rules.py`, `policy.py`, `static_rpc.py`와 `manifest.json`, `harness_console/src/platform/yield-manifest.generated.json`을 적용한다. 이 단계의 Python 파일과 `manifest.json`은 모두 `harness/gateway/` 아래이다.
3. `harness/gateway/execution.py`, `connection.py`, `events.py`에 설정 저장·steer 접수·carryover 이벤트와 바인딩을 적용한다.
4. `harness/native_ipc.py`, `hermes_chat_worker.py`, `hermes_chat.py`, `control.py` 순서로 IPC·worker·전달·종료 정산을 적용한다. 네 파일 모두 `harness/` 아래이다.
5. 프런트엔드의 `use-busy-input-mode.ts`, `use-prompt-actions/index.ts`, `message-stream.ts`, `use-web-session.ts`에 설정·전송·수신 흐름을 적용한다. 정확한 경로는 2절의 해당 파일 항목을 사용한다.
6. 작성기의 `use-composer-submit.ts`, `controls.tsx`, `index.tsx`, `queue-panel.tsx`와 `i18n/en.ts`, `HermesWebApp.tsx`, `web.css`를 적용한다.
7. 2절의 Python·프런트엔드 테스트 파일을 적용한다. `test_gateway_pr7b_unit.py`에는 이 단계에서 `cb8feec2`의 오류 코드 hunk만 적용한다.
8. 원본과 사내 diff, 파일별 mode와 보존한 사내 변경을 대조한다.
9. 이 배치의 5절을 실행한 뒤 2차 배치를 적용한다. 새로고침 복원 판정은 두 커밋 적용 후 수행한다.

#### 5.3. 실제 생성 중 입력 확인

담당자는 앞선 안내서에서 준비한 로컬 게이트웨이와 콘솔을 기동한다. 사내 개발용 모델·DB 설정을 사용하며 인증정보를 기록하지 않는다. busy를 `steer`로 두고 질문을 보낸 뒤 생성 중에 후속 입력을 보낸다. 각 모드는 별도 실행으로 확인하고 run id와 실제 종료 상태를 기록한다.

1. 선택 UI에 `진행 방향 조정`, `대기열에 추가`, `중지 후 보내기`가 한국어로 표시되는지 확인한다.
2. steer에서는 생성 중 후속 입력이 같은 run에 흡수되고 사용자 말풍선이 유지되는지 확인한다.
3. queue에서는 칩이 영어 `Queued`가 아닌 `대기 1건`으로 표시되는지 확인한다. 첫 run 완료 후 후속 질문이 별도 run으로 실행되어 두 run이 `completed`인지 확인한다.
4. interrupt에서는 첫 run이 `cancelled`, 후속 run이 `completed`이며 후속 질문에 답하는지 확인한다.
5. `queuedPaused` 문구 `대기 N건 · 일시정지`는 원본에서도 실측되지 않았다. 이 항목은 `미검증`으로 남긴다.

#### 5.4. 원본 저장소에서 확인한 사실

원본 관측 환경은 2026-11-26(Asia/Seoul), macOS, loopback `127.0.0.1`이다. steer 실측에서는 생성 중 후속 입력 후 원래 질문이 하나의 `completed` run으로 끝났고 후속 문구가 같은 대화에 반영됐다. 선택 라벨이 한국어로 보였다.

queue 실측에서는 원래 질문과 후속 질문이 두 개의 `completed` run으로 실행됐다. 한국어 칩 `대기 1건`을 관측했고 영어 `Queued`는 없었다. interrupt 실측에서는 첫 run이 `cancelled`, 둘째 run이 `completed`였고 후속 질문이 답으로 이어졌다.

`cb8feec2`만 적용한 상태에서 새로고침 후 steer 말풍선 소실을 재현했다. `1068d6a9`는 이 문제를 고친다. 이 원본 관측을 사내 결과표의 시작값에 통과로 옮겨 적지 않는다.

#### 2.1. `08-YieldAgent/harness/gateway/session_rpc.py`

`SessionRPC.history()`는 각 run의 `native_messages`에서 해당 turn을 순회한다. 기존에는 assistant와 tool 역할만 처리하여 `harness_runs.native_messages`에 저장된 생성 중 steer 사용자 행을 빠뜨렸다. 이 행은 `role=user`, `display_kind=steer`이며 content가 OUT-OF-BAND 마커로 감싸져 있다. 새로고침하면 live optimistic 말풍선이 사라지고 history에서도 행이 누락되어 steer가 보이지 않았다.

게이트웨이에서 `agent.conversation_compression`을 import하지 않는다. engine 런타임 import는 게이트웨이 venv에서 실패하므로 작은 로컬 helper `_extract_steer_text`를 추가한다. engine의 안정된 리터럴 `[OUT-OF-BAND USER MESSAGE`와 `[/OUT-OF-BAND USER MESSAGE]`를 사용하여 여는 문자열을 찾고 그 뒤 첫 줄바꿈을 건너뛴 뒤 닫는 문자열 앞까지 추출한다. 내부 텍스트를 strip하여 반환하고 없거나 비어 있으면 `None`을 반환한다.

turn 순회에 user 분기를 추가한다. content가 문자열인 행에서 `display_kind==steer` 또는 여는 리터럴 포함 조건을 만족하면 추출한다. 비어 있지 않은 결과만 `{role:user, text:inner}`로 순서대로 추가한다. 잘못된 형식이나 빈 추출 결과는 건너뛰어 마커 껍데기를 표시하지 않는다. 다른 user 행은 계속 건너뛰고 `run['query']` 처리는 바꾸지 않는다.

steer-carryover run의 남은 텍스트는 `run['query']`에서 한 번 표시한다. 추가 native user 행에는 `display_kind`와 마커가 없으므로 새 분기가 실행되지 않아야 한다. 기존 prefix slicing은 각 steer 행을 한 run의 turn에만 포함한다. REST `/gateway-m1/api/sessions/{sid}/messages`는 `history()`를 사용하므로 별도 코드 변경 없이 새 행을 전달한다. `engine/**`는 수정하지 않는다.

#### 2.2. `08-YieldAgent/harness/tests/test_gateway_pr7b_unit.py`

reload history에서 user 텍스트가 `[question, inner steer]`이고 steer가 첫 tool id 뒤, 둘째 tool id 앞에 위치하는지 검사한다. `display_kind`가 있는 경우와 없는 경우를 매개변수화하고 모든 text에 OUT-OF-BAND가 없으며 REST에서도 복원되는지 확인한다. 빈 내용·잘못된 형식·문자열이 아닌 content는 추가 행을 만들지 않고 일반 user 행도 계속 건너뛰는지 검사한다. carryover의 user 텍스트는 `[question, steer inner, leftover]`가 각각 한 번인지 검사한다. drift guard는 engine의 `prompt_builder.py`와 `conversation_compression.py`를 import하지 않고 텍스트로 읽어 AST 파싱하며, 로컬 리터럴이 `_STEER_FALLBACK_OPEN/CLOSE`와 같고 `STEER_MARKER_OPEN`이 여는 리터럴로 시작하는지 검사한다.

3. 같은 URL로 다시 새로 진입하여 말풍선 1개와 OUT-OF-BAND 텍스트 0개를 확인한다.
4. 수정 전 steer가 누락됐던 기존 세션을 연다. 저장된 native steer 행이 있으면 해당 말풍선이 한 번 복원되고 마커 껍데기가 없어야 한다.

#### 5.3. 원본 저장소에서 확인한 사실

원본 관측 환경은 2026-11-26(Asia/Seoul), macOS, 게이트웨이 `127.0.0.1:61842`, Vite `127.0.0.1:61843`이다. 전체 harness pytest는 `2040 passed, 4 skipped, 340.50s`였다. 이 값은 원본 저장소 관측이며 사내 검사 횟수나 Windows 결과가 아니다.

새 대화는 완료 직후 live 말풍선 1개, hash URL 새로고침 후 1개, 다시 새로 진입한 뒤 1개였다. OUT-OF-BAND 표시는 0개였고 `native_messages`에 `display_kind=steer` 행이 있었다. 해당 세션의 run은 하나였다. 수정 전에 만든 기존 세션을 수정 후 다시 열었을 때도 생성 중 steer 말풍선이 마커 껍데기 없이 정확히 한 번 보였다.

#### 5.4. 미검증 항목과 복원 범위

아래 네 항목은 결과표에서도 `미검증`으로 시작한다. 원본의 유닛 테스트와 macOS 관측으로 실제 UI나 Windows 결과를 대신하지 않는다.

1. 실제 steer-carryover run은 원본 UI에서 재현하지 못했다. 이 동작은 유닛 테스트만 커버한다.
2. `native_messages`가 없는 run은 history가 steer를 복원하지 않는다. 이 커밋에는 `steer.accepted` 이벤트 fallback이 없으며 해당 run의 UI 복원은 미검증으로 남긴다.
3. Windows에서 이 커밋의 pytest와 UI를 실행하지 않았다. 담당자의 Windows 실행 전까지 미검증이다.
4. `queuedPaused` 라벨은 이 커밋과 무관하며 여전히 실측되지 않았다. `대기 N건 · 일시정지` 표시는 미검증으로 남긴다.
