# 사내 Luna·Terra에 순서대로 줄 작업

## 첫 지시문

사내 레포를 열고 다음 문장을 붙여넣는다. 승인된 사내 미러로 원본을 받는 환경이면 주소만 바꾼다.

```text
현재 열려 있는 사내 레포에 수율분석 하네스를 이식하려고 해. 먼저 https://github.com/dorothy90/map_agent.git 의 codex/goal-driven-harness 브랜치를 사내 레포 밖의 별도 폴더에 받아. 사내 레포의 원격 설정은 그대로 두고, 사내 자료는 외부로 보내지 마.

받은 브랜치의 HEAD를 source-head.txt에 기록하고, docs/yield-harness-port/START_HERE.md부터 읽어. 01-merge.md의 1~3절을 실행해서 같은 HEAD의 FILES.tsv에 담긴 모든 파일과 Git 선택 경로를 검증한 다음 사내 레포와 비교해. 원본이나 설명서를 확인할 수 없으면 어느 단계에서 막혔는지 알려줘.

이전에 이식을 시도했다면 당시 비교표는 보관하고 현재 사내 코드를 기준으로 새 비교표를 만들어. START_HERE.md의 ‘이전 Windows 이식본에서 이어가기’에 있는 6개 파일도 확인해. 특히 instructions.py가 읽는 instructions/behavior.md가 사내 패키지에 포함되는지 확인해. 기존 프론트, 사내 인증, DB 연결의 변경분도 구분해서 보고해.

02-file-map.md와 04-acceptance.md의 현재 이식 범위도 대응시켜. 전체 행 조회·보고서 요약·LOT 이력·백그라운드 맵, 예약·칸반·첨부·MCP, 개인 파일·프로젝트와 웹 화면을 빠짐없이 확인해. 캡처·더미 데이터·개인 프로필·운영 키는 복사 대상에서 빼. 이번에는 비교까지만 해. Hermes 엔진, 전용 도구 6개, 백엔드, 기존 웹 프론트별로 추가할 파일 수·그대로 쓸 파일 수·충돌 수를 정리하고, 주요 충돌은 양쪽 경로와 이유를 보여줘. 사내 소스에 파일을 복사하거나 수정하기 전에 결과부터 보고해.
```

## 두 번째 지시문

비교표를 검토한 뒤 같은 사내 채팅에 아래 내용을 붙여넣는다.

```text
앞에서 기록한 source-head.txt와 현재 참조 폴더의 HEAD가 같은지 확인한 뒤 plan.tsv와 비교 결과를 기준으로 실제 이식을 진행해. 목표는 사내 기존 동작을 보존하면서 Hermes 엔진, 수율 전용 도구 6개, 백엔드, 기존 웹 프론트를 연결하는 거야.

개발 PC는 Windows, 배포 서버는 Ubuntu야. 어제 반영한 코드를 기준으로 이번 참조 커밋의 변경분을 병합해. Windows 로컬 채팅·맵·엑셀 실행 경로와 검사 명령은 06-windows-chat.md를 따라 옮겨. Ubuntu 백엔드는 SSH 서비스·전용 SSH 계정·키 없이 실행해야 해. Docker나 WSL 설치도 전제하지 마. 01-merge.md의 4절을 따라 Ubuntu의 local 실행 경로를 사용해. 모델이 생성한 Python의 사용자별 파일·네트워크 격리를 유지하고, 실제 Ubuntu에서 SSH 없이 채팅과 분석이 끝까지 작동하는지 검증해.

1. 시작점을 기록해. 사내 레포의 현재 브랜치·커밋·미커밋 변경을 확인해. 사내 기준 커밋에서 전용 이식 브랜치를 만들고, 작업 중인 변경이 있으면 별도 Git 작업 폴더(worktree)에서 진행해. 비교 이후 달라진 파일은 결정을 다시 확인해.
2. 파일별 결정을 적용해. KEEP은 그대로 두고, ADD는 사내 다른 경로에 같은 역할의 파일이 없는지 확인한 뒤 01-merge.md의 port_plan.py apply로 추가해. MERGE는 양쪽 내용을 읽고 필요한 변경만 반영해. 특히 사내 인증·권한, DB 연결, 사용자별 데이터 접근 범위, 기존 API·화면 경로를 보존해. HOLD는 이유를 기록하고 건너뛰어.
3. 충돌은 파일 단위로 처리해. Hermes 원본은 검증된 버전 단위로 유지하고 전용 도구는 등록 지점에서 연결해. 02-file-map.md에 따라 일반 채팅 자동 검색과 직원별 권한, 조회·맵 완료 워커, 예약·칸반 첨부·MCP·프로젝트·개인 파일, 프론트의 실제 호출 기록과 다운로드까지 함께 옮겨. 고정 원본 배포의 기존 리소스와 테스트 입력은 보존해. 업무 캡처와 더미 DB를 복사하거나 적재하지 마. Ubuntu 백엔드에서 HARNESS_SHARED_YIELD_DIR을 실제 공용 수율 입력 디렉터리로 지정해. 맵 도구의 공정명 입력 설명을 반영하고, 직원 프로필의 스킬 저장과 길이 검사는 Hermes 원본에 맡겨. 사내에서 쓰는 기능을 삭제하거나 기존 계약을 바꿔야 하는 경우에는 해당 파일만 보류해. 양쪽 경로, 예상 영향, 내 결정이 필요한 사항을 적고 독립적인 나머지 작업은 계속해.
4. 이식 결과를 검증해. 04-acceptance.md에 따라 ADD·KEEP 파일의 내용과 실행 권한, MERGE 파일의 실제 변경을 확인해. 사내 기존 테스트와 이식한 기능의 테스트를 실행해. 실행 가능한 환경이면 새 채팅에서 ‘수율일보 작성해줘’를 보내고 제품 하나를 선택한 뒤 표·산점도·BIN 맵이 뜨는지 사내 DB와 대조해. 실행하지 못한 항목은 이유와 함께 미검증으로 표시해.
5. 결과를 보고해. 검토한 이식 변경만 전용 브랜치에 커밋하고, 시작·완료 커밋, 추가·유지·병합·보류 수량, 주요 병합에서 보존한 사내 동작, 테스트 결과를 알려줘. 기본 브랜치 병합과 배포는 내가 검토한 뒤 진행할게. 사내 소스·로그·결과는 내부에만 보관해.
```

## 세 번째 지시문

이식 커밋을 사내 검증 환경에서 실행할 수 있을 때 아래 내용을 붙여넣는다.

```text
이식한 버전에서 사내 기존 기능과 수율 하네스가 함께 동작하는지 실제 웹 채팅으로 검증해. 두 번째 단계에서 기록한 이식 전·후 커밋을 사용하고, 브라우저에서 질문을 보내 실제 사내 모델·도구·DB를 거쳐 최종 답변이 표시될 때까지 확인해.

1. 사내 기존 기능부터 확인해. 사내 사용 예시나 기존 검수 기록에서 대표 질문을 골라. 특히 이번에 병합한 인증·도구·화면 경로를 사용하는 질문을 포함해. 이식 전·후 버전에서 같은 권한의 검증 계정, 같은 질문, 같은 데이터 기준일로 각각 새 채팅을 열어 실행해. 기대한 사내 도구가 호출됐는지, 조회 범위와 핵심 결과가 같은지, 화면에서 기존처럼 결과를 열 수 있는지 비교해. 답변 문구가 달라도 수치와 동작이 같으면 그 근거를 적어. 이전 버전을 실행할 수 없으면 기존 검수 기록을 근거로 표시하고, 확인할 수 없는 전후 차이는 미검증으로 남겨.

2. 이식한 버전에서 별도의 새 채팅을 열고 “수율일보 작성해줘”만 보내. 실제 제품 선택 목록에서 사내 DB에 데이터가 있는 제품 하나를 골라. 실행 기록에서 수율일보 스킬이 로드됐는지, 선택한 제품이 실제 도구 호출 인자에 반영됐는지 확인해. 검사 종류를 따로 고르지 않아도 PT1H·PT1C 데이터가 있는 만큼 함께 조회되는지 봐.

추가로 같은 계정의 새 대화 두 개에서 같은 공용 CSV로 표와 맵을 요청해. 04-acceptance.md의 공용 파일 검수 절차에 따라 자기 세션의 산출물만 열리는지 확인해.

3. 최종 화면과 DB를 대조해. 결론 아래에 최근 월별 3개월·주별 4주·일별 3일 표가 뜨는지, 이어서 최근 두 주의 열화·개선 각 3개 파라미터가 웨이퍼 단위 산점도로 보이는지 확인해. 각 검사별 BIN 맵은 같은 BIN 순서로 최대 10열, 직전 주·최근 주·델타 순서로 3행이어야 해. 같은 제품·검사·기간·재측정 기준으로 사내 DB를 독립 조회해. 표의 기간별 수율, 산점도 한 점의 LOT·웨이퍼·측정값, 맵 한 좌표의 두 주 발생률과 델타(%p)를 실제 화면 값과 나란히 기록해. 표본이나 BIN이 적으면 DB에서 가능한 수와 화면에 표시된 수를 비교해.

4. 같은 채팅에서 방금 결과의 제품이나 기간을 다시 적지 않고 후속 질문을 보내, 선택 조건을 유지하는지 실제 도구 인자와 답변으로 확인해. 대화 목록에서 이 채팅을 다시 열었을 때 표·산점도·맵이 다시 보이는지도 확인해.

같은 직원으로 새 채팅을 열어 “이전 채팅에서 본 맵 조건을 찾아 다시 그려줘”라고 해. 실행 기록에서 이전 채팅 검색 결과와 확인 카드를 대조해. 후보 하나면 추천 선택지로, 여러 채팅에서 서로 다른 조건이 나오면 출처별 선택지로 표시되는지 봐. 확인 전 대상 맵 조회가 시작됐는지와 선택 후 실제 맵 인자가 선택한 조건과 일치하는지를 기록해. 선택지 구성을 위한 제품·공정 목록 조회는 대상 맵 조회와 구분해.

별도 새 채팅에서 04-acceptance.md의 RCP별 누적 맵 두 턴도 실행해. 실제 요청 모델 ID와 후속 질문에 전달된 선택 이력, 전용 맵 도구 인자, 화면 수량을 기록해. 정확한 공정명과 오타를 각각 새 채팅에서 시험해. 04의 자동 검색 검수에 따라 직원별 도구 목록, 모델이 보낸 공정명과 DB 목록 확인 순서, 실제 맵 수량을 대조해. 자동 스킬 저장 여부와 재시도 횟수는 관찰값으로 기록해. 개발 더미 DB의 GLM 기준 결과와 사내 실측을 구분해.

같은 채팅에서 새 Python 변수를 다음 질문에 재사용하고 웨이퍼 맵을 넣은 엑셀을 요청해. 04-acceptance.md의 채팅별 Python·파일 검수에 따라 화면의 다운로드 버튼을 직접 누르고 파일 안의 이미지와 좌표·BIN을 사내 DB와 대조해.

웹 채팅과 두 모델 평가(수율 도구 비활성, 가상 자료)에서 실행 기록이 모두 stock_chat인지 확인해.

Windows에서는 06-windows-chat.md에 따라 WSL·Docker 없이 제한 분석 실행기를 먼저 검사해. 브라우저의 같은 채팅에서 4SA 웨이퍼 맵을 조회한 뒤 엑셀을 실제로 내려받아 맵 이미지와 좌표·BIN을 사내 DB와 대조해. Ubuntu 배포 검증은 Ubuntu 서비스 계정에서 별도로 진행해.

04-acceptance.md의 ‘현재 이식 범위의 실제 채팅 검수’ 표를 모두 실행해. 실제 자료가 없어 장시간 집계가 발생하지 않거나 사내 MCP 연결 권한이 없으면 해당 시나리오의 미검증 사유를 기록해. 테스트 예약은 검증 후 취소해.

5. 시나리오별로 질문, 기대 결과, 실제 결과, 통과·실패·미검증을 표로 보고해. 실제 채팅 화면 캡처와 해당 실행 ID를 사내 검증 폴더에 남겨. 차이가 나면 최초로 어긋난 지점과 근거를 적어. 접속·권한·모델·DB 문제로 실행하지 못한 항목은 미검증으로 표시해. 이번 단계는 검증과 보고까지야. 코드 수정이나 배포는 별도로 결정하고, 화면과 로그는 사내에만 보관해.
```
